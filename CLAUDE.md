# CLAUDE.md

## This fork

This is a **fork of Excalidraw** that adds two custom systems on top of upstream:

1. **Version control / time travel** — a semantic version log built by observing the store's durable increments, with jump, selective undo (skip a change), dependency analysis, and interactive conflict resolution. See [Version control](#version-control-time-travel).
2. **Hard alignment** — a persistent "alignment lock" between elements: aligned elements move and resize together to maintain a shared edge, or a shared spacing. See [Hard alignment](#hard-alignment).

`terminology.md` (repo root) is the glossary for both systems — read it first. `VERSION_CONTROL_PLAN.md` covers the version-control design in depth, and `limitations.md` records the behaviour that is deliberately bounded or left unsolved — check it before treating a rough edge as a fresh bug. Upstream tests are not maintained: the fork has diverged too far for them to say much, and a full run takes about an hour. Their snapshots are kept at upstream's originals (as on `master`) and never regenerated, so a red upstream test is not a regression. When editing, match the surrounding code's comment density and idiom.

## Project Structure

Excalidraw is a **monorepo** with a clear separation between the core library and the application:

- **`packages/excalidraw/`** - Main React component library published to npm as `@excalidraw/excalidraw`
- **`excalidraw-app/`** - Full-featured web application (excalidraw.com) that uses the library
- **`packages/`** - Core packages: `@excalidraw/common`, `@excalidraw/element`, `@excalidraw/math`, `@excalidraw/utils`
- **`examples/`** - Integration examples (NextJS, browser script)

## Development Workflow

1. **Package Development**: Work in `packages/*` for editor features
2. **App Development**: Work in `excalidraw-app/` for app-specific features
3. **Testing**: Run the fork's own tests for what you touched, by path (`yarn vitest run <paths>`, e.g. `packages/element/tests/alignmentSolve.test.ts`). Don't run `yarn test:update` — it would rewrite upstream snapshots
4. **Type Safety**: Use `yarn test:typecheck` to verify TypeScript

```bash
yarn test:typecheck  # TypeScript type checking

```

## Version control (time travel)

Lives in **`packages/excalidraw/versionLog/`**. It observes the store rather than replacing history: `VersionLog` subscribes to `Store.onDurableIncrementEmitter`, and each durable increment becomes one **Moment** (our user-facing unit — deliberately *not* the same as Excalidraw's `DurableIncrement`; see `terminology.md`).

Key files:

- **`VersionLog.ts`** — the in-memory log. Ingests increments, holds Moments, tracks the cursor (current Moment), inactive (skipped) Moments, filters, and `onChangeEmitter` (a payload-less "something changed, re-pull" signal the sidebar subscribes to). It also holds a linear undo/redo expressed as skips: `undo()` deactivates the newest active Moment at or before the cursor and pushes it onto a redo stack, `redo()` reactivates the top one, and a new Moment clears the stack. `UNDO_THROUGH_VERSION_LOG` (`actions/actionHistory.tsx`) chooses between this and Excalidraw's own history for Ctrl+Z / Ctrl+Y and the toolbar buttons. Excalidraw's history commits with `CaptureUpdateAction.NEVER`, so the log never sees it and the next replay brings an undone change back.
- **`classify.ts`** — turns raw per-element `LogEntry` deltas into semantic `LogOperation`s (move, resize, group, `arrow-bind`, `alignment`, …). Runs pre-passes for multi-entry gestures (grouping, alignment lock/unlock) and **consequence detection**: a change caused by another (a bound arrow following its element, or a hard-aligned partner following its driver) is absorbed into the causing op's `consequentOps` instead of surfacing separately — one user action, one op. Each absorbed op also records *why* it followed (`ConsequenceReason`): the alignment detector's adjacency graph tags every edge with the relationship that made it — edge alignment, gap chain, or group membership, most specific winning where a pair is coupled twice — and a breadth-first walk out from the driver gives each follower the kind of edge it was first reached on, which is the relationship holding that follower rather than one further upstream. Arrow followers are always bindings. The panel draws the reason as an icon on the consequent row. `getChangedKeys` is the central key-diff chokepoint. Phantom link changes — `alignments` / `gapAlignments` rebuilt into an equal array, which the store diffs by reference and so reports as changed — are stripped from the entries themselves by `stripPhantomLinkChanges` before any classifier runs, so the `raw` op's property list never shows them either; an increment left with nothing real gets no Moment at all. The same pre-pass folds a bound text's derived `fontSize` onto its `baseFontSizeVC` (see [Bound-text auto-fit](#bound-text-auto-fit)), so the log reports the size the user picked and auto-fit churn disappears.
- **`types.ts`** — the `LogOperation` discriminated union, `LogMoment`, `getOperationElementIds`. Adding an op kind means updating every exhaustive switch (see below).
- **`applyOps.ts`** — replays a `LogOperation[]` forward/backward against a scene snapshot. Replay does **not** run the alignment solver — consequent ops are what reproduce alignment followers. Bound arrow ends are derived instead: after every op, `followBindings.ts` re-places the arrows bound to whatever it changed from their bindings' `fixedPoint`, as upstream does mid-drag, and a binding consequent that recorded absolute points is not replayed. Recorded points would put the end where the element was when the follow happened, which a skipped Moment makes wrong.
- **`replay.ts`** — selective-undo engine: replays from a baseline, skipping inactive Moments; also uses `reserveReplayVersion` / `highWaterVersion` so replayed elements always out-version the store snapshot (the store gates on strict `version <`). The log never records `boundElements` — an update carrying only bookkeeping (`TRACKING_PROPS`) is dropped before classification — so `syncBoundElements` rebuilds every list from the arrows' bindings and the labels' `containerId` after the walk.
- **`dependencyAnalysis.ts`**, **`remap.ts`** — dependency edges between ops, and conflict remapping when a selective undo removes a referent.
- UI: **`components/VersionLogPanel.tsx`**, **`VersionLogMomentCard.tsx`** (+ `VersionLogPanel.scss`, whose `--vlog-*` custom properties are the single place to theme the panel), **`VersionLogConflicts.tsx`**.
- **Conflict resolution** is a session, not a dialog. A toggle that leaves ops without a referent opens `AppState.versionLogResolution`: every conflict starts as a skip, `replayActiveOps(log, tentative)` layers the session's decisions over the log's remaps (still reporting their conflicts, so the choice can be offered again), and the canvas shows each result as it is chosen, with view mode held on so nothing can be edited. A decision that exposes a new conflict gets a skip too, and the replay re-runs until every conflict has one. Apply writes the decisions as remaps; Cancel reverts the toggle. Stand-ins are picked on the canvas; a bar floating over the top of the canvas pane (`VersionLogConflicts.tsx`, mounted in `LayerUI`'s wrapper like the toolbar) holds the help text — what went missing, worded the same whatever the state — plus a three-way switch per missing referent — Show before (a replay with the toggle reverted, which Apply then keeps, as Cancel does), Skip, or Reassign, the only mode in which the canvas washes everything but the candidates and takes a pick — then Cancel and Apply, which is disabled while a Reassign has no stand-in, and a chip per missing referent when there are several. `excalidraw-app` holds its autosave for the session. On the canvas the active conflict's candidates stand out of a wash over everything else, the chosen one outlined solid, and the missing referent is drawn as a ghost where it was before the toggle (`renderer/renderConflictResolution.ts`; the ghosts come from the scene captured when the session opened). Clicking a candidate picks it, clicking it again goes back to a skip, and anywhere else pans. The click and the outlines share `versionLog/conflictPicking.ts`, so what is drawn as pickable is what a click picks: the editor's own hit test (`App.getElementsAtPosition`), so a pick lands where a selecting click would, topmost candidate first, passing over elements that can't stand in. A candidate the log deletes later than the conflict has nothing on the canvas, so it can't be picked. Hovering a candidate previews choosing it: one replay under that choice, cached per candidate until a decision changes, with every element it would draw differently (`drawsDifferently`) shown as a ghost through `versionLogHoverPreview`. Hovering anything else outlines it, labelled on the canvas with why it can't stand in. The reasons come from `standInRefusal` in `replay.ts`, asked at the conflict's own point in the replay alongside the candidates and kept as `PendingConflict.refusals`. An element with no entry wasn't there yet, which is its own answer.

**Adding a `LogOperation` kind** requires updating every exhaustive `switch (op.kind)` / `Record<LogOperation["kind"], …>`: `getOperationElementIds` + `OP_COLOR` map, `applyOpToScene`, `getWrittenProperties`, `applyRemapsToOp`, `findMissingReferents`, `computeHoverPreview`, and `renderOpContent`.

## Overlap-aware move up / down

Upstream's "move up" / "move down" step one element (or group, frame, container-with-text) at a time whether or not it overlaps, so most presses change the stacking order without changing anything on screen — and the log would record each one. The fork's `getOverlappingTargetIndex` (`packages/element/src/zindex.ts`) keeps stepping past units the selection doesn't overlap and lands just past the first one it does; with nothing overlapping in that direction the press does nothing, so no increment and no Moment. Overlap is axis-aligned bounds, so boxes that cross with nothing drawn in the crossing (two diagonal lines) still count. Bring to front / send to back are unchanged: "front" means above everything, including what the element may overlap later.

The log records stacking order as a `reorder` op holding each moved element's fractional `index` before and after. `extractReorder` (`classify.ts`) lifts every `index` change in an increment into one, whatever gesture made it; one that rides along with another op — binding lifts an arrow above its element, grouping gathers the members — is `incidental` and gets no row of its own. Ops write the key only, and `replayActiveOps` orders the snapshot by `index` before returning it, since the commit's `syncInvalidIndices` treats array order as the truth.

## Arrow editing without the editor

Upstream bends a non-elbow arrow with more than two points only inside the linear editor. The fork treats every arrow the way upstream treats elbow arrows: a selected arrow shows its segment midpoints, dragging one adds a point, and double-clicking a point between the ends deletes it (`App.handleCanvasDoubleClick`). `LinearElementEditor.hasMidpointsOutsideEditor` is the one predicate the midpoint rendering and hit test consult. Lines keep upstream's rule, and Ctrl+double-click still opens the editor.

## Bound-text auto-fit

Upstream grows a *container* when its bound text no longer fits — whether the text grew (typing) or the box shrank (resize). That turns a one-axis resize into a two-axis one and lets a label overrule a size the user set. This fork inverts it: the **text** is refitted instead, by font size.

- **`fitBoundTextToContainer`** (`packages/element/src/textElement.ts`) is the single answer to "what font size fits?". Wrapped width and height are both monotone in font size, so it bisects between `MIN_FONT_SIZE` and the authored size. Three outcomes: `fits`, `refit` (write these values), `overflows` (no allowed size fits).
- **`ExcalidrawTextElement.baseFontSizeVC`** is the size the user chose; `fontSize` is derived from it and the container's size. Recorded from the first fit onward and never cleared — measuring against it is what lets a shrunk text grow back. It is the fork's counterpart to upstream's `baseFontSize`, which does the same job for sticky note labels only; the two stay separate because upstream reads a non-null `baseFontSize` as "this is a sticky label". `isAutoFitBoundText` says which text the fork fits, and upstream's `getBaseFontSize` / `getBaseFontSizeUpdate` pick the right field, so every place a user sets a size — the font picker, the Stats panel, paste-styles — writes both `fontSize` and `baseFontSizeVC` without knowing about either.
- Called from three places, all of which used to grow the box: `handleBindTextResize` (resize), `refreshTextDimensions` (live typing — `redrawTextBoundingBox` only runs on submit, so the live path is the one that matters), and `redrawTextBoundingBox` itself. Each runs on *every* pass, not just overflowing ones, since growing back needs a trigger too. The old growth branches remain as the `overflows` fallback.
- `resizeSingleElement` refuses a frame whose proposed size `overflows`, holding the element at its current size — which is the last one that fit, since every earlier frame passed the same check. Arrow labels are excluded throughout: their box is a fraction of the arrow, not a size anyone set.

## Element short ids

`ExcalidrawElement.shortId` (`R3`, `A7`, `T1`) is a human-readable second name for an element, running **alongside** Excalidraw's `id` — a 20-odd character random string that is fine as a key and useless to read off a card. Nothing keys off the short id.

- **Allocation**: `packages/element/src/shortId.ts`. A letter per element type plus a per-letter counter. `assignShortIds` is called from `Scene.replaceAllElements`, the one chokepoint every element passes through however it arrives (drawn, pasted, imported, replayed) — and the only place that sees the whole scene, which is what makes the duplicate check possible: paste and duplicate copy the field, so a name is kept by the first element to claim it and the rest are re-issued. Counters start above the highest name in use *including deleted elements*, so a name is never recycled under a log entry that still refers to it.
- **Written in place**, not through `newElementWith`: the name labels an element that already exists rather than editing it, so it must not bump the version or land in the undo stack. `shortId` is in `classify.ts`'s `TRACKING_PROPS` for the same reason — an increment carrying only a name is not a Moment.
- **On canvas**: drawn just above each element's top-left corner (`drawElementIdLabel`), on the *interactive* canvas so it never reaches an export, and only while the version-log sidebar is open — that is when the question "which one is R3?" arises. Bound text is skipped; its label would land inside its own container.
- **In the log**: `formatElementLabel` prefers the short id over the element type ("Moved R3"), resolved at render time through `useShortIdOf` — deleted elements included, since a `delete` op names something already gone from the canvas.

## Hard alignment

A persistent alignment constraint stored **as element data**, distinct from Excalidraw's transient *snapping* — but defined by the same geometry: a hard alignment is a soft edge coincidence the user has chosen to keep.

- **Data model**: `ExcalidrawElement.alignments?: readonly ElementAlignment[]` (see `packages/element/src/types.ts`). Each link is `{ elementId, axis, selfEdge, otherEdge }` — a per-axis coupling to a partner, with an edge per side so cross-edge alignment (one element's right to another's left) works. Links are symmetric (stored on both partners). Persisted through `data/restore.ts`. A pair may be linked at **several places on one axis** (same-width elements share left, centre and right); `getAlignedLinks` emits one link per shared *coordinate*, so link identity is `(partner, axis, selfEdge, otherEdge)` — never `(partner, axis)`. **Links never outlive or outnumber their partners.** A duplicate starts with none (`duplicateElement` strips them — its links would name the original's partners, which hold no link back); the anchor flag is the element's own and is copied. Deleting an element releases every link naming it from the survivors (`releaseAlignmentsToDeleted`, beside `fixBindingsAfterDeletion` in the delete action and in the eraser), in the same captured update so one undo restores both sides; a gap chain that loses a member is dropped whole. `restoreElements` prunes the same way on load (`pruneAlignmentLinks`), for files saved before that — only in its whole-scene `repairBindings` branch, since a partial restore would read every partner outside it as gone.
- **Engine**: `packages/element/src/alignment.ts` — detection (`getAlignedLinks`, `getAlignmentGuides`), link editing (`lockAlignmentPair` / `unlockAlignmentPair` for one guide, `lockAlignments` / `unlockAlignments` for a whole selection), and the two entry points `dragAlignedElements` (from `dragElements.ts`) and `propagateAlignmentsAfterResize` (from `resizeElements.ts`). Both are thin: they ask the **solver** (`alignmentSolve.ts`) what everything does, spread the answer across groups, and write once through `applyAlignmentDeltas`. The engine lives in `packages/element` because those callers are there; `packages/element` can't import `snapping.ts` (a `packages/excalidraw` module), so alignment and snapping can't be one file.
- **UI**: selecting an element shows every alignment it currently has — persisted ones solid, live soft coincidences dashed — each with a badge between the two elements — the middle of the gap, or of their overlap when there is none — drawn as the line itself (`drawAlignmentBadge`): a bar along the guide's own direction, solid on a filled disc when hard, a faded rim-to-rim hairline when soft. Clicking it toggles that one link between soft and hard, so the indicator *is* the creation UI. There is no modal gesture. Geometry is shared between the renderer and the pointer handler via `getAlignmentGuideLines` (`renderer/renderAlignmentLocks.ts`), so a click hit-tests exactly what is drawn; both badges consume pointer-down but fire on pointer-up. A **concentric pair** — two elements linked (or linkable) centre-to-centre on both axes — would put both padlocks on the shared centre, so `pairCentredGuides` folds them into one badge carried by the x line, where the two bars cross into a **crosshair**; each arm shows its own link's state, so a half-kept pair still reads. Clicking it releases both when both are kept and otherwise keeps whichever isn't (`setAlignmentPairsLocked`). Storage is unchanged — still two centre links — and the version log names such an op a *centering* by reading the links (`isCenteringAlignmentOp`). **Alt+Shift+L** / the context menu strips all links from the selection (`actions/actionAlignmentLock.tsx`).
- **Anchors**: `ExcalidrawElement.alignmentLocked` marks an element that alignment must never move — toggled by the anvil drawn over the centre of a single selected element (currently a hand-drawn path; see the deferred backlog). Like the guide badges it consumes pointer-down, so a press there toggles rather than drags. Test it with **`isAlignmentAnchor`**, never the raw field: upstream's `locked` implies anchoring too. An anchor neither moves nor changes size, and it is the only thing that can make a gesture impossible — everything else accommodates. The anvil overlay (`renderAnchorLockOverlays`) names anchors two ways: *refusing* (filled — the gesture is impossible and they are why) and *permitting* (outlined — it went through, but they shaped where things landed). For a resize the answer depends on the transform handle, which the renderer never sees, so `App.maybeHandleResize` computes it (`getAlignmentResizeEffects`) and publishes it as `appState.alignmentResizeConstraints` — the refusing, active and released constraints per axis — and `alignmentResizeStretchAnchorIds` (both transient, unobserved by the store, cleared on pointer-up); for a drag, `getAlignmentMovers()` answers it directly. `getAnchorOverlays` reads those into the anvils to draw. A refusal also draws **the alignments carrying it**, which come from the solve itself: every row carries a `ConstraintRef` naming what it came from, and a row that contradicts the ones before it reports the set it contradicts (`AlignmentResponse.refusedBy`, per axis). A resize that had to give up its held edge reports `releasedBy` the same way. Those lines draw as any enforced guide does, except that they **flash** — `getRefusalFlashColor` pulses them from the indicator red to a deeper one on a 600ms cosine, a change of shade rather than of anything structural — and so do their badges, which also swell slightly on the same beat (`getRefusalFlashScale`). A numbered cluster holding a flashing badge opens as though hovered, since a count can say *that* something in it refused but not which. The anvils named in a refusal or a release flash and pulse too, from their own warning red to the same peak, with their own pulse amplitude since an anvil is scaled to its element rather than fixed on screen. Clamps flash the same way: the gesture code reports what a drag or resize is resting against (`dragSelectedElements` returns it, `transformElements` hands it to a callback) and `App` publishes it as `appState.alignmentClampBlame`, transient like the rest. A gap closed to contact flashes its chain, and an element squeezed to its minimum size — `MIN_ALIGNED_SIZE` for a partner the solve stretches, `MIN_RESIZE_EXTENT` for the resized element itself (or the narrowest member of a multi-element resize) — is covered by a translucent red block that flashes and swells on the same beat (`drawMinimumSizeWarning`). The flash is also what keeps the canvas repainting: a refused gesture is usually held still against the constraint, so the scene carries an `alignmentRefusal` runtime in its animation state for as long as anything is flashing (the same mechanism the binding highlight uses). The anvil says *who* refused and the lines say *through what*.
- **The solver** (`packages/element/src/alignmentSolve.ts`): every hard alignment is linear in per-edge displacements, so a gesture is one small linear system. Each element gets two unknowns per axis, `δmin` and `δmax` (an `EdgeDelta`) — a translation is the two equal, a stretch is them differing, which is what lets a partner *change size* to accommodate a drag or resize rather than only move. **The edge a resize handle holds still is offered, not imposed** — its row has all-zero gesture coefficients, so it is added after the hard rows and declined when they contradict it. It is the third entry in `ALIGNMENT_FEEL_ROWS` (`resizeHoldsItsOtherEdge`), and turning it off means the row isn't offered at all: nothing then asks that edge to stay, and since translating costs a millionth of what stretching does, the handle drags the element rather than resizing it. An element centred on an anchor then resizes *symmetrically* about that centre instead of being refused, and `buildResizeAlignmentDeltas` writes the driver's own geometry (only for a lone unrotated driver, since a rotated element's bounds aren't its `x`/`width` and a multi-element resize places members from the box's scale). Every edge the gesture actually moves stays hard, so the opposite side can never take over the resize. The declined offer's witness is reported as `releasedBy` — the constraints that forced the element to change shape in a way the user didn't ask for — so those lines flash and the anchors among them take the *outlined* anvil (the gesture went through; they only shaped it). The resize is seeded from the **gesture** rather than from the driver's geometry (`ResizeIntent`): once alignment writes the driver's own edge, a seed measured off that geometry no longer reads as "this edge is held", and the answer alternates frame to frame — the element springs back and forth for as long as the pointer is down. **Hard rows**: each edge link (`expr(e, selfEdge) = expr(f, otherEdge)`, centre = mean of the two edges), each gap chain (consecutive gaps equal), each anchor (both edges 0), the gesture itself, and a *rigidity* row (`δmin = δmax`) for elements a constraint must not resize — rotated ones (their bounds aren't their width and height, so stretching would couple the axes) and text (a width change rewraps it). **The only refusal is inconsistency**: rows are reduced incrementally (`createRowReducer`), and a row that contradicts the ones before it makes the gesture impossible on that axis. Where the rows leave freedom, a KKT solve minimises `WEIGHT_STRETCH·‖stretch‖² + WEIGHT_TRANSLATE·‖translation‖²`, so *move-else-stretch* falls out globally; the ratio is written with the expensive side at 1 because placing the big number on stretch drops the Schur complement below the singularity tolerance and every solve reads as infeasible. Everything is homogeneous in the gesture, so the answer (`AlignmentResponse`) is a *linear response*: one `EdgeDelta` per element per gesture degree of freedom (1 for a drag, 2 for a resize), evaluated with `applyAlignmentResponse`. Feeding it symbolic seeds (1 for "this edge moves", 0 for "it doesn't") makes the same solve answer the UI's questions before any geometry changes, so prediction and act cannot drift apart. **Every row carries a `ConstraintRef`** naming what it came from — link, chain, anchor, rigidity, feel rule, or the gesture — and the reducer keeps, per kept row, the combination of original rows behind it. One solve then answers every question asked of it: `refusedBy` (the rows a contradiction is between, which is blame, exact and per axis), `activeConstraints` (non-zero multiplier: the answer is pressed against them), `implied` (a row the others already imply — a releasable duplicate), `stretchCauses` (per stretched element, the load-bearing rows naming it) and `freedom` (unknowns minus rank). `blockers` is the anchors among `refusedBy`, and `alignmentAnchorsInPlay` the anchors among `activeConstraints` — both were release-and-retest, one extra solve per anchor per frame, until the rows could say it themselves. The one place "load-bearing" and "releasing it would change the answer" come apart is an anchor whose work a *declined feel rule* would have done anyway, which `alignmentAnchorsInPlay` subtracts. The clamps report the same way: `ClampBlame` names the gap or the extent the tightest bound came from. `ALIGNMENT_BLAME_PLAN.md` has the design. The guides read `activeConstraints` to decide what to draw during a gesture — a link is drawn when it is *carrying* the gesture (or refusing it), **or** when it belongs to a selected element, whether or not its partner moves. The second half is what keeps the alignments a gesture is *about* on screen; the first replaced "both its ends are moving", which counted a link the gesture satisfies for free — both ends dragged directly, or both carried by one group — as though it were doing work. `stretchCauses`, `implied` and `freedom` are reported but not drawn yet. **Groups are not rows** — `spreadAcrossGroups` is a post-pass over the solved deltas (see `limitations.md` for what that costs). `ALIGNMENT_SOLVER_PLAN.md` has the full design.
- **Gap alignment (equal spacing)**: the n-ary sibling of edge alignment, in `packages/element/src/gapAlignment.ts`. A **chain** of three or more elements ordered along an axis whose consecutive gaps are all equal, stored as `ExcalidrawElement.gapAlignments` — the *identical* `ElementGapAlignment` record on every member, so a member's role is just its index in `ids` (no reciprocal form to keep in sync). Detection reimplements gap enumeration because `packages/element` can't import `snapping.ts` — the same wall that keeps the two systems in separate files. Soft chains are reported **maximal** (`addMaximalChain` grows a seed triple outward), so four evenly spaced elements are one guide rather than the two triples inside it.
- **Gap alignment — the feel rules**: a chain driven from a single point has one free degree of freedom (its slope), and a minimum-disturbance solve would pick it badly — the far end drifts *against* the drag. Two rules pin it, offered to the row reduction after the hard rows and kept only if they fit (`ALIGNMENT_FEEL_ROWS`, which toggles each so the difference can be compared): an *end* member driven → the **far end does not move** (both edges, and all-or-nothing, since holding one edge would let the chain stretch it instead), so the run compresses between the two ends with every gap giving up an equal share; an *interior* member driven → the rest of the chain **travels rigidly** with the driven member's centre (both edges again, and for the same reason: told only where its centre goes, a member with an edge an anchor holds gets there by stretching). A rule the hard rows contradict — an anchored member overriding the far-end default — is declined, not approximated, and the chain reshapes around the anchor. The same rules apply to drag and resize, so the same displacement of the same edge moves a chain the same way whichever gesture caused it. The numbers each choice produces are asserted in `alignmentSolve.test.ts`.
- **Gap alignment — clamps**: `clampDragToGapAlignments` and `clampSizeToAlignments` stop a gesture at contact rather than refusing it. Every gap, and the extent of every element the solve stretches, is affine in the gesture, so each contributes one bound and the tightest interval wins. Crossing is forbidden because past zero a chain reorders and equal gaps in the *new* order need the outer elements to be the same width; squashing through zero width puts an element's edges the wrong way round, so every link naming one starts reading the other. The resize cap covers only single-element resizes of an unrotated driver (see `limitations.md`). A resize is also clamped to `MIN_RESIZE_EXTENT` (`resizeElements.ts`) so a handle can no longer fold an element through itself. A flip swaps which side is `min` and which is `max`, so every *stored* link naming an edge starts reading the other one and jumps by the element's width — and for a gap chain it is a reordering, which the drag path already refuses at contact for the same reason. Single-element resizes floor the pointer-derived size; multi-element ones bound the box's **scale** instead (`clampMultiElementResize` — the narrowest member reaches the floor first, so clamping the box itself would put every member below it) and clear `flipByX`/`flipByY`, since there the size is an absolute distance from the anchor and grows again past the crossing. The clamp is unconditional rather than alignment-specific: a handle that folds through on some shapes and stops on others is worse than either rule. Flipping remains available through the flip actions.
- **Gap alignment — merge**: locking a chain that continues one already locked merges them (`lockGapAlignment` → `asOneChain`), so A—B—C plus C—D—E becomes one five-member link rather than two enforced, drawn, separately-unlockable links. A candidate is absorbed only if it shares a member *and* the union is still a single evenly spaced run; the search repeats to a fixed point, since a new chain can bridge two existing ones. An existing link is replaced only when its members are a **contiguous run** of the new chain — a chain through every other element covers different gaps and survives as its own constraint. Unlocking drops the whole chain, whichever badge is clicked.
- **UI**: an equal-gap guide draws each gap as a capped span — solid hard, dashed soft — with **an equals badge on each** (`drawEqualsBadge`, not the edge guides' padlock: a padlock means "this pair is pinned", an equals sign means "these gaps are the same size"). A badge per gap, because the assertion is an equality *between* them, and because the single natural midpoint is already the anchor anvil's spot. Every gap draws on one shared perpendicular coordinate (`GapAlignmentGuide.across`), matching where upstream's transient gap snap line sits. Gap guides stay up **during a drag** — soft ones swap their badges for upstream's midpoint ticks, since there is nothing to click mid-drag — and `renderSnaps` is handed the gaps they cover so it can drop its own duplicates, which are drawn one per satisfied snap at their own perpendicular offsets. A soft chain's span is likewise suppressed where a hard chain already draws that gap, so the merge candidate shows exactly one unlocked badge on the new gap.
- **Version-log integration**: lock/unlock is an `alignment` op, anchoring is an `alignment-anchor` op; alignment-induced moves are absorbed as `consequentOps` (see `classify.ts`). The `alignment` op carries a `field: "alignments" | "gapAlignments"` discriminator rather than splitting into two kinds — that would mean eight more exhaustive-switch arms for what is one gesture with two payloads.
